Proxmox MCP & AMD-APU GPU-ML

▸ MCP control plane

A Python stdio MCP server (bsahane/mcp-proxmox) exposing 40+ Proxmox tools, registered at user scope so it loads in every session.

The load_dotenv cwd trap

Gotcha: the server calls load_dotenv() with no path, which only finds .env when the process's working directory is the repo. An MCP client spawns servers from an arbitrary cwd, so the token silently never loads and every call fails auth. Verified: find_dotenv() returns '' from any foreign cwd.

Fix — a cwd-pinning wrapper

#!/usr/bin/env bash  — run.sh
cd "$(dirname "$0")" || exit 1
exec .venv/bin/proxmox-mcp
claude mcp add -s user proxmox-mcp -- ~/dev/mcp-proxmox/run.sh
Why it works: the MCP handshake is stdio — stdout is a protocol channel. The wrapper keeps it a single exec'd process, and the server writes logs to stderr only, so the JSON-RPC stream stays clean regardless of who launches it.

▸ The LXC 400 bug

Every LXC-targeted tool — list, info, start, stop — returned 400 Bad Request. One root cause, four call sites.

The client resolved a container's node with /cluster/resources?type=lxc. Proxmox's type only accepts vm · storage · node · sdn — containers come back under type=vm, distinguished by a per-entry type field.

 QueryOutcome
Beforeresources.get(type="lxc")invalid enum → HTTP 400
After[r for r in get(type="vm") if r["type"]=="lxc"]valid query, then filter
Fix symmetrically. Both resolvers get the guard: the LXC resolver keeps type=="lxc", the VM resolver keeps type=="qemu" — so a VM tool now correctly rejects an LXC id instead of mis-dispatching it to the wrong endpoint.

▸ Power-cut auto-recovery

A stopped guest coming back after an outage is a three-layer chain — and only the bottom layer is reachable over the API.

LayerWhat it doesWhere
1 · BIOSBox powers on when mains returns (AC Power Loss → Always On)console / BIOS
2 · HostProxmox boots + starts guest-autostartconsole
3 · Guestonboot=1 + startup orderingAPI ✓

Layer 3 — DNS leads, in order

pct set 103 --onboot 1 --startup order=1,up=15  # pihole: DNS first, then a 15s beat
pct set 100 --onboot 1 --startup order=2       # docker-host: after DNS is answering
Caveat: layer 3 only helps once the box is already powered and booted. A genuine outage still needs the two physical BIOS/console toggles — they can't be flipped over the network, and on a headless mini-PC they need a borrowed screen once. Shutdown runs in reverse order, so DNS stays up while workloads drain.

▸ GPU backends: Vulkan vs ROCm

An AMD APU that used to hard-reset under GPU ML on a bare-metal desktop install. The question was never "is the GPU broken" — it was "what was colliding."

Root cause: the resets were ROCm compute and a Wayland compositor (Hyprland) contending for the same shared iGPU — two subsystems fighting over one GPU. Headless Proxmox removes the compositor half, so the collision structurally can't recur.

Both backends, measured (Radeon 680M, gfx1035)

BackendSetupResultPrefillDecode
Vulkan/dev/dri · llama.cpp · RADVstable, 5-min soak1061 t/s54 t/s
ROCm/dev/kfd · PyTorch · gfx1030 overridestable, 500 matmuls~1.7 TFLOP/s FP32
CPU baselineZen3+ · 8 coresreference415 t/s46 t/s
Read the split: prefill is compute-bound → GPU wins 2.56×; decode is memory-bandwidth-bound and this is a UMA part (iGPU + CPU share LPDDR5, no matrix cores) → only ~1.2×. Default to Vulkan (simplest — /dev/dri only, no override); reach for ROCm only when you need the PyTorch/HIP ecosystem.

▸ Docker-in-LXC GPU recipe

Running a ROCm container inside a privileged Proxmox LXC needs every one of these, or it fails in a different place each time.

Container config (/etc/pve/lxc/<id>.conf)

features: nesting=1
lxc.apparmor.profile: unconfined       # else runc: error mounting "proc" ... permission denied
lxc.cgroup2.devices.allow: c 234:* rwm  # /dev/kfd  (ROCm compute)
lxc.cgroup2.devices.allow: c 226:* rwm  # /dev/dri  (render)
lxc.cgroup2.devices.allow: c 10:229 rwm # /dev/fuse (storage driver)
Storage driver is the trap: native overlay2 is blocked in LXC (mount overlay: permission denied), and the default vfs has no copy-on-write — it ballooned a 30 GB image to 140 GB and filled the disk. Fix: fuse-overlayfs via /etc/docker/daemon.json.

Run it

docker run --rm --device /dev/kfd --device /dev/dri \
  --security-opt seccomp=unconfined --group-add video \
  -e HSA_OVERRIDE_GFX_VERSION=10.3.0 rocm/pytorch:latest ...
The override is a masquerade. HSA_OVERRIDE_GFX_VERSION=10.3.0 runs gfx1030-tuned kernels on gfx1035. Core tensor ops (rocBLAS matmul) are proven; validate exotic kernels (some conv/attention/fused ops) per workload.

▸ iGPU workload fit

A real but modest accelerator: ~1.7 TFLOP/s, UMA, no matrix cores. Fit the workload to the hardware.

VerdictWorkloadsWhy
Do it on GPULLM inference · embeddings/RAG · Whisper · DL-OCR · vision-LLM doc/receipt parsingInference & prefill-bound — where the 2.5× lands
Temper itSmall-model LoRA fine-tuning · Stable DiffusionRuns on ROCm, but slow — tinkering, not volume
Stay CPU / offloadTraining at scale · high-throughput servingBandwidth-bound; UMA starves where dedicated VRAM would help
Two guardrails: run GPU jobs containerised and headless (never beside a compositor again), and remember Tesseract is CPU-only — no GPU benefit. For receipt/doc OCR the GPU-friendly path is a vision-LLM via Vulkan, where the image becomes a big prompt (prefill-heavy).
